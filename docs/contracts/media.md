# Owner media API contract

Direct services and production examples default to disabled media. After Q33/Q34 integration review, the development launcher and Compose explicitly select private local storage, preserving existing local photo upload behavior; `MEDIA_STORAGE_BACKEND=disabled` overrides that choice. Production enablement requires the deployment-specific GCS acceptance gates. The lifecycle and client have local review and test evidence recorded in Q32–Q34.

All management endpoints require a currently authenticated, email-verified account. Asset and idempotency identifiers are opaque; a key is scoped to the account. Supply a unique `Idempotency-Key` (1–128 URL-safe ASCII letters, digits, underscore or hyphen) per selected file. Keep it across retries and cancellation. `POST /v1/me/media` takes the raw file as its body, with `Content-Type` matching JPEG, PNG or WebP. The server enforces a 10 MiB streaming limit, 20 megapixels and 32,768 pixels per side, still images only, and strips metadata after applying orientation. It responds with `{id, state, description, display_url, thumbnail_url}`. States are `pending`, `ready`, `rejected`, `deleted`. Repeating a key returns the same asset; reuse for different bytes is a 409. Upload may return a terminal result synchronously; clients must not assume this. Status: `GET /v1/me/media/{id}` or `GET /v1/me/media/by-key/{key}`. Cancellation before an ID is known: `DELETE /v1/me/media/by-key/{key}` creates a durable cancellation tombstone even if the POST has not started. `DELETE /v1/me/media/{id}` is idempotent; deletion of an asset referenced by a draft or retained published listing projection returns 409 until neither references it. `PATCH /v1/me/media/{id}` takes `{description}` (plain text, at most 500 characters). Owner-only previews are `GET /v1/me/media/{id}/{display|thumbnail}` and require Authorization; browser clients can fetch bytes and use an object URL. A management DTO never contains storage paths or processing details.

`AdvertBody` accepts ordered `media_ids` alongside the existing ordered external HTTPS `images` list. The combined maximum is 30, with external images first followed by owned IDs in order. Every ID must refer to a ready asset owned by the caller. Legacy `images` must not contain this service's media URLs. Publishing materializes display URLs; thumbnail URLs can be obtained by replacing the final `/display` with `/thumbnail` only for owned-media URLs. Descriptions persist with assets; clients may use the description as alt text. Public `GET /v1/media/{id}/{display|thumbnail}` requires a previously published projection in a currently visible, non-hidden canonical listing. Withdrawn and saved-delisted listings retain the existing listing-detail access policy; unpublished draft attachments are never public. Erasure immediately denies the media and requests byte deletion. Cache policy is no-store so moderation and erasure take effect on future requests (already downloaded bytes cannot be recalled).

Errors: 401 missing/invalid/closed session; 403 unverified or another owner's asset; 404 unavailable asset or public rendition; 409 key reused with different bytes or asset still referenced; 408 body-read timeout; 413 body exceeds 10 MiB; 415 unsupported or mismatched media type; 422 invalid image, animation, excessive dimensions or too many images. Responses do not reveal filesystem paths, source metadata or decoder errors. Derivative writes use generated keys, not client filenames. Orphaned assets are eligible for cleanup after 24 hours only when neither a draft nor a retained published projection references them; retries and deletion are idempotent. Storage cleanup failures remain retryable. Restore a database and matching object-store backup together, or forward-fix and rerun cleanup; do not roll back an applied migration destructively.

An interrupted request or 413 leaves a pending key that can be retried; invalid images make the key rejected, and deleted or rejected keys cannot be reused. Ready retries must carry the same bytes or return 409. Pending, rejected and deleted DTOs have null rendition URLs. Cancellation and deletion return the management DTO. Processing is limited to one concurrent upload body and decode per API process.

Configure local storage with `MEDIA_STORAGE_BACKEND=local` and a run-specific `MEDIA_DIRECTORY`; configure a browser-reachable `MEDIA_PUBLIC_BASE_URL`. GCS requires `MEDIA_STORAGE_BACKEND=gcs`, `MEDIA_GCS_BUCKET`, and the cloud dependency; no bucket is created. Media defaults to disabled; production API enablement requires GCS and an HTTPS public base. Schedule `PYTHONPATH=backend python -m realtoruch.media` (one sweep), or run `PYTHONPATH=backend python -m realtoruch.media --loop --interval 3600` for hourly sweeps with graceful shutdown under the API database role to delete unattached assets older than 24 hours. The storage service must provide durable private access and conditional creates; orphan cleanup must be monitored and retried on error.

The body-read deadline is 30 seconds once an upload receives the processing slot; an interrupted or timed-out pending upload can be retried.

A remote PUT that timed out may still complete after erasure. For GCS, permanent deletion installs empty markers using generation preconditions at both rendition keys; these fence late create-only writes. An unconfirmed fence fails erasure so it can be retried. Erasure retains a private, scrubbed cleanup tombstone (opaque asset and account IDs only, plus a server-derived key) until both fences are confirmed; deleted assets needing cleanup are retried without waiting 24 hours. Confirmed erasure tombstones are removed, while owner-deletion tombstones preserve the idempotency key. An open-account deleted row retains its internal digest until both fences succeed; a null digest means no storage write began or both fences are confirmed. Closed-account tombstones scrub the digest immediately and remain eligible for cleanup until purged. The dedicated GCS bucket must retain the live zero-byte fence objects and must not apply a lifecycle rule that deletes them. Temporary GCS deletion is generation-matched so a delayed delete cannot erase a later replacement. Object versions, backups and live provider behavior require deployment-specific verification; no live GCS acceptance is claimed.

Migration 011 is complete for both tasks: media references are ordered opaque IDs in the existing advert draft JSON, not a new relation table. Attachment writers and cleanup share the existing per-account transaction fence. Q33 must not alter the 011 SQL or checksum.

The bounded account export includes owned, non-deleted media ID, state, description and creation time, but excludes storage keys, idempotency keys, digests and binary contents. This is additive to the existing export and respects its overall byte limit.
