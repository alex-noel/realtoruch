# Notification inbox continuation

`GET /v1/me/notifications` remains account-scoped and returns `items`, `unread_count`, `page`, and `page_size`. Existing `page`/`page_size` offset callers continue to work. Responses additionally contain `has_more` and `next_cursor` (a string when more rows exist, otherwise `null`). New clients request older rows with `cursor=<next_cursor>` and the same `page_size`; when a cursor is supplied, it takes precedence over `page`. Malformed cursors are rejected. Cursors represent a position, not an authorization grant: every request is filtered to the current account.

Ordering is `created_at` descending and `id` ascending. The cursor is opaque to clients and resumes strictly after the last returned pair, including ties. This is keyset traversal, not a snapshot: new rows before the cursor appear on a head refresh, while rows inserted after it may appear in a later page. `has_more` is determined by fetching one extra row; it is authoritative at query time. The client keeps its loaded older rows on head refresh. If the new head overlaps loaded rows, it preserves the tail cursor; if a full new head is disconnected from them, it restarts traversal from the new head cursor so that intervening rows remain reachable. An empty prior inbox also adopts the new cursor. Merged rows are deduplicated by ID and sorted in server order. A page response from an older continuation cannot replace a restarted cursor.

The client permits one load-more at a time, retains rows and cursor on failure, and exposes retry. Read requests are independently guarded by notification ID; a failed read leaves the row unread. Successful reads update only the requested row and invalidate older in-flight head results. Account reset fences page and read completions and clears private data and pending state.
