# Deployment preparation (not executed)

Terraform was validated locally. Helm templates were rendered and Docker Compose configuration was checked. No cloud project, resource, deployment, image registry push or git push was created. These instructions describe remaining operator work; they are not an authorization to deploy.

## Local development

Install Python 3.12 and Node 24 LTS (Node 22.13+ is also supported), then run `make install` and `make dev` from the repository root. The launcher creates private `.local/` SQLite databases and random development secrets, seeds fictional data once, and starts API :8000, auth :8001, rental alerts, account mail/deletion jobs and Expo :8081. Ctrl-C stops its child processes. Demo records never load implicitly in production.

For the separate live catalog, run `make collect` and then `make live`. These commands use `config/sources.live.json` and `.local/live-rentals.db`, without demo seeding. Collection is bounded and runs once unless `ARGS="--loop"` is supplied; it does not install a background scheduler. See [source configuration](source-connectors.md) for per-source limits, rechecks and collection reports.

For the PostgreSQL + Elasticsearch local topology, start Docker Desktop, then use `docker compose up --build`. Database and Elasticsearch ports are not published; the three HTTP services are bound to localhost. The local Compose ES instance disables authentication only inside its isolated Docker network. Open the frontend separately with `cd apps/mobile && npm run web`. Compose uses explicitly development-only credentials; it is not a production manifest.

## Physical mobile devices

The same app code exports iOS and Android JavaScript bundles. Run `make mobile-check` to report prerequisites. This machine currently lacks full Xcode and Android SDK/platform tools, a maps key and production HTTPS endpoints. An actual native build still needs those tools, signing and device/simulator QA. Set the frontend's `EXPO_PUBLIC_API_URL` and `EXPO_PUBLIC_AUTH_URL` to reachable HTTPS services, or your computer's LAN IP for development. For LAN testing, launch the Python services with `--host 0.0.0.0` and explicitly set CORS to your web preview origin if needed; the default dev launcher binds only localhost. Use `npx expo start --lan`, and launch through a compatible Expo Go or a development build. iOS uses Apple Maps; Android builds require a restricted `GOOGLE_MAPS_ANDROID_API_KEY`, read by `app.config.js`. Never put server secrets in `EXPO_PUBLIC_*` variables. Native tokens use SecureStore; browser access tokens stay in memory and refresh tokens use HttpOnly cookies. Web and auth should be on the same HTTPS site (for example `rentals.example.com` and `api.rentals.example.com`) for SameSite=Strict cookies.

## Cloud sequence

1. Select an existing billed project and review capacity/cost. Bigtable and streaming Dataflow are material fixed costs even with few listings. No cost estimate was invented in this repository.
2. Configure a private versioned GCS Terraform state backend and a state-access role. Supply `terraform.tfvars` from the example. The default GKE control plane is private: the operator needs VPN/bastion access to its VPC. Confirm region/quota availability. Run a reviewed Terraform plan before any separately authorized apply.
3. Build immutable `cloud` and `dataflow` Docker targets, scan them, and push only after deployment authorization. Pin image digests for production. The example base image tags and Dataflow launcher `latest` must be resolved to reviewed digests in the release pipeline.
4. Apply the full ordered registry in `infra/sql/migrations.json` with an operator/schema-owner connection, then apply `infra/sql/grants.sql` with the Terraform-created IAM usernames (`realtoruch-api@PROJECT.iam`, etc.). For existing saved searches, run `python -m realtoruch.worker baseline-searches` once before starting the alert evaluator. Runtime users must not own the schema. Account upgrades invalidate legacy access-only sessions, so existing users sign in again.
5. Create a 3072-bit RSA signing pair. Auth alone receives the private key; API/auth receive the public key. Populate per-service Secret Manager versions from locally secured JSON, not Terraform variables or source control. `config/production-secrets.example.json` illustrates the API shape. Supply actual random secrets, never example placeholders. The application runtime fetches its own secret with Workload Identity before starting.
6. Prepare each service's configuration using the table below. SQL connections use Cloud SQL Python Connector, private IP and automatic IAM authentication. No permanent SQL password or public SQL endpoint is needed. Kubernetes config must use namespace `realtoruch`, matching the Terraform Workload Identity bindings. The current chart assumes Terraform's default resource name `realtoruch`; keep it or update chart identities/secret names together.
7. Bootstrap Elasticsearch with a strong local Kubernetes secret `elasticsearch-bootstrap/password` and TLS secret `elasticsearch-tls` containing `tls.key`, `tls.crt`, and `ca.crt`. Certificate SANs must include `elasticsearch` and its cluster DNS names. Create a read API key restricted to the `rentals-search` alias and its physical indices for search, and a writer key for indexer with the rebuild/alias privileges described below. Configure `ELASTICSEARCH_CA_FILE=/etc/elasticsearch/ca.crt`. Never disable TLS verification. Elasticsearch is private; the public service offers validated `/v1/search` queries.
8. Render/review the chart with the immutable cloud image and configured sources; deploy only after separate authorization. API ingress exposes `/v1`, auth/search routes, API docs and health endpoints. `/internal` and metrics have no ingress route. Cluster network policies limit ES traffic to search and indexer. Configure DNS to the Terraform API address and wait for managed TLS issuance.
9. Build a Dataflow Flex Template spec from `infra/dataflow/metadata.json` and the `dataflow` image, upload to the staging bucket, then set its existing GCS URI and enable the job. Workers run with private IPs, private SQL access and a dedicated identity. Set explicit worker sizing/limits for expected load. Enable collectors only after the Dataflow consumer and source access are ready.
10. Export the web app with production API/auth URLs baked in. Upload **only** `apps/mobile/dist` to the public web bucket. Use immutable long cache headers on hashed assets and a short/no-cache policy for `index.html` and `service-worker.js`. The worker handles push only and does not cache authenticated API responses. Set DNS for the CDN hostname. Replace demo map tiles with a licensed production tile service and retain attribution.
11. Enable uptime checks after DNS/TLS/readiness work. Exercise failover, restore, collector interruption, Dataflow redelivery, search outage fallback, API rate limits and contact retention before claiming an application SLA. Validate account verification/recovery and rental alerts against the actual email provider; these use separate confirmation flows.

It mounts the same source ConfigMap into API and collector and sets `CONNECTORS_CONFIG=/config/sources.json` for both, so `/v1/sources` reports the configured sources. Review the source entries and request budgets before enabling them. The local live configuration demonstrates the three implemented portal parsers; it does not imply production collection or complete portal coverage.

## Email and device notifications

Email is the primary out-of-app channel. The API queues a confirmation to the signed-in account email; only confirmed addresses receive rental alerts. Confirmation links expire after one hour. Every email includes an unsubscribe link; account settings can disable/re-enable delivery. No password or auth database access is given to the rental API or alerts worker.

The local launchers default to `EMAIL_DELIVERY_MODE=file` and write private, ignored `.local/mail/*.eml` previews. Open a preview to follow its confirmation or account recovery link. To configure actual SMTP, copy `config/mail.env.example` to `.local/mail.env`, set mode `smtp`, replace host/sender/credentials, set file permissions to 600 and restart the launcher. Explicit shell environment overrides that file. No real email is sent by the default demo/live commands. Provider credentials and a verified sender have not been supplied or tested.

Set the following in API, auth and alerts configurations: `EMAIL_DELIVERY_MODE=smtp`, `SMTP_HOST`, `EMAIL_FROM` (a verified sender), and `PUBLIC_WEB_URL=https://your-web-host`. Auth/auth-worker and alerts secrets additionally contain `SMTP_PORT` (default 587), `SMTP_SECURITY=starttls` (or `ssl` for implicit TLS), and `SMTP_USERNAME` / `SMTP_PASSWORD` if required. API needs no SMTP credentials. TLS, a real sender and HTTPS links are enforced in production; configure the chosen mail provider's sender/domain requirements before enabling delivery. Failed mail sends are retried with backoff, up to eight attempts. Inspect private `email_deliveries` and `auth_jobs` status/error-class counts; SMTP acceptance does not establish delivery to the inbox. Account-erasure jobs retry until completion and must be monitored. Protect confirmation messages and recipient data as private account data.

Optional browser push uses a VAPID P-256 pair: API receives `VAPID_PUBLIC_KEY` and `VAPID_SUBJECT`; alerts receives `VAPID_PRIVATE_KEY` and the same subject. A local pair is generated once in ignored `.local/development-secrets.json`. Production subject must be a real operator contact URI. Serve the web app on HTTPS, retain `/service-worker.js` at the origin root, and enable alerts from a user gesture. Restrict `WEB_PUSH_ALLOWED_HOSTS` to the actual browser providers. Endpoints, key material and Expo tokens never appear in public listing responses.

Optional mobile push requires `EXPO_PUBLIC_EAS_PROJECT_ID` at build time, configured APNs/FCM credentials, and a physical development/release build. Set `EXPO_PUSH_ENABLED=true` in API/alerts and, if used, `EXPO_PUSH_ACCESS_TOKEN` in alerts only. The worker checks Expo receipts, disables expired registrations, and never resends an accepted ticket while waiting for its receipt. Native delivery remains unverified without these credentials/device. Email works independently of native push setup.

## Local operational checks

`make reliability ARGS="--cycles 3 --interval 60"` runs bounded real collection into the live catalog and records `.local/reliability.json`. Provider pacing/backoff still applies. `make load-check ARGS="--requests 50 --concurrency 4"` reads four public endpoints on loopback only. For an intentional 200-request local capacity sample, start the local API with `REQUEST_LIMIT_PER_MINUTE=10000`; do not change production throttling. Results describe that machine/catalog only.

`make backup-check ARGS="--catalog live"` uses SQLite online backups for the selected catalog and shared auth database, then restores each into a fresh temporary file and compares integrity, foreign keys and table counts. `make postgres-backup-check ARGS="--container YOUR_DISPOSABLE_CONTAINER --user rentals"` requires the explicit container label `realtoruch.verification=true`, initialized rental/auth schemas and quiescent test data. It runs custom-format `pg_dump`, restores into newly created databases, compares table counts and sorted-content digests, then removes only its own restore databases. It never overwrites existing databases and refuses unlabelled containers.

Private dumps/checksums remain in `.local/backups/`. They are not off-machine backups and contain private account data; choose retention/encryption before operational use. Both local restore paths passed. Cloud SQL point-in-time recovery still needs a separate drill.

On Apple Silicon, use native ARM64 container images. A shell-wide `DOCKER_DEFAULT_PLATFORM=linux/amd64` forced an emulated Elasticsearch image that could not start its seccomp sandbox during testing; running the ARM64 image fixed startup without disabling sandbox protections.

## Operational limitations

- This is one regular node and one zone. Pod budgets cannot protect against a node/zone failure; Elasticsearch can be rebuilt from SQL after a disk failure. SQL backups/PITR and raw observation retention are configured but restore has not been exercised.
- Bigtable is a managed Google service accessed through Google APIs with Private Google Access and IAM, not a database process with a GKE pod IP.
- The Dataflow template spec, container images, Secret Manager versions, SQL grants and Elasticsearch TLS/API keys must exist before dependent workloads start. Terraform intentionally does not generate secrets or push artifacts.
- Production per-IP throttling lives in Cloud Armor (20 auth requests/minute, 120 public requests/minute). Local in-process throttling is disabled in production to avoid treating a shared load-balancer IP as one user. Keep the ingress attached to the policy.
- Monitor pending outbox size, Pub/Sub oldest unacknowledged message, collector CronJob failures, unknown/stale source count and invalid-event subscriptions. The provided monitoring includes uptime/SLO and Pub/Sub backlog alerts; the remaining dashboards and notification recipients need operational configuration.
- Search is eventually consistent. REST falls back to SQL when search is unavailable. SQL keyword matching and Elasticsearch full-text relevance differ; source status and filters are the same contract.
- Recheck rate and source retention must match actual supplier agreements. No portal permission is inferred from robots.txt or public visibility.

## T28 deployment review checklist

The migration manifest `infra/sql/migrations.json` is authoritative: apply every registered rentals migration (001–006, 008–010; 007 is reserved for T11 and unused) and auth migration (001, 004, 005), in order, with a schema-owner identity, then `infra/sql/grants.sql`. Runtime IAM users are not schema owners; the API cannot connect to auth SQL and search has no SQL role. The cloud collector uses Bigtable and Pub/Sub and has no SQL role. The local Compose demonstration still uses a shared development owner and is not a least-privilege role test. Dataflow can cancel pending delivery work when a listing is delisted; constrain its secret and private execution environment accordingly. Validate IAM database usernames and exact privileges against the deployed database after migration, including `SELECT FOR UPDATE`.

The search key needs read access to the `rentals-search` alias and its physical `rentals-search-*` targets (and legacy `rentals-v1` during migration). The indexer needs index create, read, write, alias management for those names, and cluster monitoring; verify the exact Elasticsearch role privileges against the pinned version before deployment. Preserve the single Recreate indexer during rebuilds. Never expose ES externally. The chart defaults to a single core e2-standard-4 in europe-central2-a, and collection is off; enabled collection uses separately autoscaled Spot nodes. Core requests total 1,100m CPU and 3,712 MiB memory (API 150m/384Mi, auth 100m/384Mi, search 100m/256Mi, Elasticsearch 500m/2048Mi, indexer 100m/256Mi, alerts 100m/192Mi, auth-worker 50m/192Mi); retention adds 100m/256Mi temporarily. Against the machine’s nominal 4 vCPU and 16 GiB, this leaves 2,900m and 12,672 MiB before Kubernetes/system reservations, monitoring, and surge replicas; actual allocatable and headroom must be measured on the node before approval. A stopped, disrupted or unavailable single node/zone interrupts service; PDBs do not provide an availability guarantee and rolling surges may not schedule.

The scheduled retention job shares the indexer service identity and configuration. Its SQL privileges therefore include expired-contact scrubbing, stale-source status updates, canonical recomputation, search/alert queue insertion and narrowly scoped pending-delivery cancellation. It cannot create or delete canonical homes, change source URLs, or read delivery recipients/tokens. The role test invokes the actual retention operation twice on a stale synthetic home and verifies its contact removal, unknown status, one revision/outbox/event and cancelled delivery claims. Splitting maintenance into a separate identity later requires changing the CronJob, IAM/secret bindings and grants together.

Before a review, replace `network.sqlCidr` with the actual private service range and verify GKE dataplane metadata/DNS and Cloud SQL connector egress. The policy permits DNS, metadata and HTTPS; provider/Google API HTTPS is not domain-restricted by Kubernetes NetworkPolicy, so enforce narrower provider boundaries with an approved egress gateway/firewall if needed. SQL ports are limited to SQL-using workloads, with database privileges separating auth and rentals. SMTP egress is limited to delivery workers. Validate network policy enforcement, private Google access, queue paths and SMTP provider connectivity in the target environment; none was exercised in cloud here.

The API and auth `/metrics` endpoints require `X-Internal-Key` using the same service's `INTERNAL_API_KEY`. A private scraper must be explicitly labeled `realtoruch-metrics-scraper=true`, obtain that key from an approved secret store, and scrape `/metrics` over a protected private connection; no scraper or credentials are deployed by this chart. Before deployment the operator must choose and install the scraper, configure targets `api:8000/metrics` and `auth:8000/metrics`, provision each service’s `INTERNAL_API_KEY` as the corresponding `X-Internal-Key` request header, authorize access to the secret, and provide private transport protection. The chart does not supply the scraper image, identity, secret references or TLS configuration. Configure TLS/network isolation for that hop. Worker readiness checks are read-only dependency/config checks, not evidence of SMTP delivery; auth-worker also checks the API cleanup readiness path. Set a termination grace period appropriate for in-flight work and verify shutdown/lease recovery under deployment conditions.

The CDN backend is a separate public static bucket using origin headers, not the API ingress. Only immutable public hashed assets may receive long cache headers; index HTML and service worker need revalidation. The public API BackendConfigs add `Cache-Control: private, no-store` to responses; account, tokens, messages and personalized API responses must bypass shared caches. Verify the actual ingress and any additional proxy before production; the `install_http` middleware also sets no-store on normal application responses, including private routes; early middleware error responses should still be checked at every ingress/proxy. No cloud resource, DNS update, image push or real mail was created by this local task.
